> 状态：2026-10-23 定稿基线，进入实现。协议字段为 v0 草案，落地时允许按实现微调，
> 但「服务端权威 + 座位视角快照 + 重进码」三条不变。

| 项 | 决定 |

## 1. 目标与非目标

### 目标

- 大厅可创建/加入幺筒房间，选 4/8/16 庄。
- 四人桌：真人占座，空位由服务端 AI 补位；断线后 AI 托管，凭重进码回座。
- 服务端是唯一权威：洗牌、发牌、动作合法性、胡牌/结算、计时与托管都在服务端。
- 每个座位只收到自己可见的状态（他人手牌隐藏）。
- 一局/一场结束的「继续」屏障、开局动画回执、整场结束与再来一场。
- 双客户端 WS 冒烟 + 规则对拍 + 前端单元测试。

### 非目标（后置）

- LLM 座位、服务端 TTS、LLM 台词。
- 联机牌谱、AI 分析、赛后复现。
- 观战、跨房迁移、排行榜。
- 手机端专门适配（沿用现有横屏入口）。

## 2. 总体架构

```
Vue 客户端
  ├─ 大厅 / 房间面板（REST：建房、加入、准备、开局）
  ├─ useYaotongRemoteGame（房间会话 + WS 权威适配）
  └─ useYaotongPort（现有演出层：开局、动作字、鸡/杠/结算动画）
        ▲ yt_snapshot（按座位裁剪）
        │ action / opening_done / continue / auto / ping
FastAPI 后端
  ├─ api/rooms.py          房间生命周期（复用，新增 matchLength）
  ├─ game/yaotong_room.py  幺筒房间：座位、重进码、驱动、快照
  ├─ core/yaotong/         幺筒规则引擎（从 TS 1:1 移植）
  ├─ ws/game_ws.py         /ws/room/{id}（新增 yaotong 分支）
  └─ storage/              rooms/matches 增加 match_length
```

原则：

- **REST 管资源，WS 管实时对局**。开局必须由 `POST /api/rooms/{id}/start` 触发，
  保证 `game_task` 绑定 uvicorn 事件循环（与经典/血流一致）。
- **服务端权威**：客户端只发「意图」，服务端校验后推进；客户端不跑本地引擎、不跑 AI。
- **快照是唯一真源**：每次状态变化广播按座位裁剪的 `yt_snapshot`；客户端以快照补状态、
  以事件流做演出。
- **房间外壳复用**：座位、重进码、准备、开局屏障、继续屏障、看门狗、落库照血流房间的实现，
  不塞进经典 `GameManager`。

## 3. 身份与鉴权

- 登录：`GET /api/login/wakudemo` → OAuth PKCE → HttpOnly Cookie → `GET /api/login/session`。
- 联机身份：服务端从会话推导 `wakudemo-<uid>`，客户端提交的 `playerId` 忽略。
- 建房/加入/查房/房间列表：`require_wakudemo_login`。
- 座位操作（ready/leave/character/close）：`rejoinCode` 校验。
- WS 握手：`/ws/room/{room_id}?rejoin_code=...`；重进码即座位 bearer 凭据，30s 内最多 5 次。
- 本地开发：`WAKUDEMO_LOGIN_BYPASS=true`；测试用假 Cookie `lgm_wakudemo_session: <uid>`。
- **MVP 不做 WS Cookie 二次校验**；若后续要收紧，在握手处比对
  `seat.player_id == f'wakudemo-{uid}'`，并保留测试旁路。

## 4. 房间模型

### REST 字段

`POST /api/rooms`：

```json
{
  "mode": "east",
  "capacity": 4,
  "rulesetId": "yaotong",
  "matchLength": 4,
  "llmEnabled": false
}
```

- `capacity` 固定 4；`mode` 仅为兼容旧表/旧客户端，幺筒不使用。
- `llmEnabled` 必须为 false；传 true 返回 `LLM_NOT_ENABLED`（MVP）。
- `matchLength` 只允许 4/8/16。

`GET /api/rooms/{id}` 增加 `matchLength`；`start` 请求忽略 `llmSeats`。

### 数据库

`rooms` 与 `matches` 增加：

```sql
match_length INTEGER NOT NULL DEFAULT 4
```

- 不改 `rooms.mode` 的 `CHECK (mode IN ('east','hanchan'))`，避免 SQLite 重建表。
- SQLite：`PRAGMA table_info` + `ALTER TABLE ... ADD COLUMN`。
- PostgreSQL：`information_schema.columns` + `ALTER TABLE ... ADD COLUMN`。
- `BaseStorage.create_room/create_match` 增加 `match_length=4` 参数；旧调用默认 4。
- 统计/历史暂按 `mode` 展示；幺筒 UI 从房间响应读 `matchLength`。

### 房间状态

- `status`: `lobby / playing / finished / error / closed`。
- 座位 4 个；`capacity=4`；空位开局由 AI 补足。
- 房间限时 60 分钟；对局中不回收；看门狗沿用。
- 房主离开顺延；全员离开解散；对局中不允许关闭。

## 5. 规则引擎移植

从 `src/game/variants/yaotong/` 移植纯逻辑，**不做表现层**：

| TS | Python | 说明 |
| --- | --- | --- |
| `tiles.ts` | `app/core/yaotong/tiles.py` | 108 张、固定鸡、牌名、洗牌/拆墙 |
| `types.ts` | `app/core/yaotong/types.py` | 状态/命令/结算数据类 |
| `hands.ts` | `app/core/yaotong/hands.py` | 计数、听牌、可胡形、过手/首摸判断 |
| `settlement.ts` | `app/core/yaotong/settlement.py` | 胡型、鸡分、杠分、幺筒责任、杀报/包牌、流局赔听 |
| `engine.ts` | `app/core/yaotong/engine.py` | `create_game / act / continue_game / self_options / kong_options` |
| `ai.ts` | `app/core/yaotong/ai.py` | 服务端补位 AI（贪心 EV，先与前端同策略） |
| `mode.ts` | `app/core/yaotong/mode.py` | 新手模式输入保护（服务端仍做合法性校验） |

移植要求：

- 1:1 翻译，不重新设计规则；随机数显式注入，保证同种子可复现。
- 物理牌守恒（108 张）与分数零和在引擎内断言。
- 规则夹具：从 TS 生成 `fixtures/*.json`（开局 + 动作序列 + 期望终态/结算），
  Python 测试直接读同一份 JSON。
- 服务端 AI 先用同一套贪心策略；LLM 后置。
- 新手/老手模式：规则与计分一致；老手模式的「常驻等 15s」由服务端计时，
  客户端只显示 `deadlineAt`，避免客户端篡改。

## 6. WS 协议 v0

### 握手

`rejoin_ok` 在经典字段上增加：

```json
{ "kind": "rejoin_ok", "seat": 0, "rulesetId": "yaotong", "matchLength": 8, ... }
```

随后立即发一份 `yt_snapshot`。

### 服务端 → 客户端

```json
{
  "kind": "yt_snapshot",
  "matchId": "...",
  "round": 1,
  "dealer": 0,
  "matchLength": 8,
  "matchFinished": false,
  "seat": 0,
  "opening": { "dice": [3, 5], "wallSide": 2, "reservedStacks": 3 },
  "roundResult": null,
  "continuation": null,
  "view": { ... }
}
```

`view` 按座位裁剪，草案字段：

```text
seat, phase, dealer, current, serial
wallCount, dice[2], wallSide, reservedStacks
matchLength, dealerRound, handNumber, repeats
players[]:
  seat, name, avatar, characterId, playerKind, isLlm=false, score
  hand            // 仅本家；他家 []
  concealedTileCount
  melds[]         // tile, kind, from, pre, chicken, responsibility
  river[]         // tile, chicken, stage, firstChicken, followChicken, pre, id
  declaration, draws, discards, drawn(仅本家), afterKong, burned,
  passedHu, chickenPeng[], chickenDiscard[]
pending: null | {
  kind: 'discard' | 'rob' | 'hot', tile, from, discard,
  choices: { seat: 'hu'|'peng'|'kong'|'pass' },
  waitingSeats: seat[]
}
ownOptions: null | { hu, peng, kong, restrictedHu, restrictedPeng, mandatory, h, shapePoints }
events[]: { id, kind, seat, tile?, chicken?, afterKong?, rush?, text }
result: null | Settlement（结算时给全量 transfers/deltas/values）
```

隐藏规则：

- 他家 `hand` 恒为空，`drawn` 恒为 null；`concealedTileCount` 保留。
- `pending` 不下发他家 `options`（避免泄露可胡/可碰），只下发 `choices` 与 `waitingSeats`。
- 牌墙只下发 `wallCount`，不下发牌序。
- `result` 在结算快照才给；赢家手牌与点炮信息按规则公开。

### 客户端 → 服务端

```json
{ "kind": "action", "serial": 12, "action": { "type": "discard", "index": 3, "declare": false } }
```

动作集合（与本地 `Command` 同构）：

```text
{ type: 'original', declare: bool }
{ type: 'discard', index: int, declare?: bool }
{ type: 'respond', action: 'hu'|'peng'|'kong'|'pass', plan?: string, deferHu?: bool }
{ type: 'hu', plan?: string }
{ type: 'declareHu', plan?: string }
{ type: 'passHu' }
{ type: 'kong', tile: int }
```

- 服务端校验：座位、阶段、`serial`、当前 `pending`/自摸窗口、动作合法性。
- `serial` 与快照一致；不匹配返回 `STALE_ACTION`，非法返回 `INVALID_ACTION`。
- 其他消息：`{kind:'auto', enabled}`、`{kind:'opening_done', round}`、
  `{kind:'continue', round}`、`{type:'ping'}`。

### 节奏与屏障

- 开局：发牌后先发 `opening` 快照；等所有在线真人 `opening_done`（60s 兜底）再开首回合。
- 局末：发结算快照；等在线真人 `continue`（20s 兜底；客户端 10s 倒计时）。
- 服务端节奏表：沿用 `PACE_MS`/`AI_DELAYS` 的可读延迟；演出不阻塞状态推进过久。
- 断线：该座位由 AI 托管；重连 `rejoin_ok` 后发全量快照，不重播开局动画。

## 9. 分阶段与验收

### M0 契约与骨架（小）

- 后端 `yaotong` 规则集/`matchLength`/DB 迁移/API 字段。
- `YaotongRoomSession` 最小骨架：建房→加入→准备→开局（空引擎快照）→解散。
- 前端 roomApi/session/大厅入口。
- 验收：两个假 Cookie 客户端能建房、占座、准备、开局、收到 lobby 快照。

### M1 规则与对拍（关键路径）

- `tiles/types/hands/settlement/engine/ai/mode` Python 移植。
- 同种子 golden 对拍（开局、出牌、碰/杠/胡、结算、流局赔听）。
- 验收：Python 单测全绿；TS/Python 同种子终态一致。

### M2 房间 + WS（可打完整场）

- 幺筒房间驱动、AI 补位、托管、开局/继续屏障、快照裁剪、动作校验。
- `yt_snapshot` + 命令集；双客户端 WS 冒烟打完 4/8/16 任一庄。
- 验收：无越权手牌；结算零和；断线重连回原座位；超时托管。

### M3 前端联机（可玩）

- `externalAuthority` + `useYaotongRemoteGame` + 大厅/房间面板。
- 联机下开局、出牌、碰杠胡、结算、继续、退出/暂离。
- 验收：浏览器双窗口完成一场；与单机演出对齐；无控制台错误。

### M4 收口

- 全量测试、构建、文档更新。
- 可选：WS Cookie 二次校验、hard 模式 15s 计时完善、统计页 matchLength。

## 10. 风险与待定

1. **房间外壳第三次复制**：经典 `RoomSession` 约 1,753 行、血流 `BloodFlowRoomSession` 约 1,074 行；
   幺筒再复制一份维护成本高。MVP 先复制血流外壳，后续再抽共享基类，避免一次性大重构。
2. **hard 模式 15s 常驻等**：服务端计时与客户端显示需要严格同口径；MVP 先保证合法动作与托管，
   计时细节在 M2/M4 补齐。
3. **前端演出接缝**：`useYaotongPort` 直接绑定 `useYaotongGame`；若 `externalAuthority` 分支过多，
   改为「游戏源」接口，保持演出层不动。
4. **协议字段**：v0 以本文件为准；实现时如需调整，先改文档再改两端。
5. **LLM/回放/分析**：全部后置；现有经典/血流代码不受影响。
